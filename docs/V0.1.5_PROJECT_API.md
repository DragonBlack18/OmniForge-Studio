# OmniForge Studio v0.1.5 — integração entre projetos por APIs locais

## Como utilizar

1. Cadastre os projetos em **Meus projetos** (v0.1.4). Cada projeto continua em sua própria pasta.
2. Inicie manualmente o servidor HTTP que o outro projeto já oferece, ouvindo em `127.0.0.1`. **O OmniForge não inicia, compila nem executa código de terceiros.**
3. Abra **Conectores de projetos** e selecione o projeto provedor. Registre `id`, nome, `http://127.0.0.1:PORTA/rota`, método GET ou POST, timeout (100–10.000 ms) e um schema JSON de entrada e saída.
4. Na automação do projeto ativo, adicione o bloco **Chamar projeto por API**, selecione o projeto e a capacidade, e conecte sua entrada JSON com um nó de gatilho/lógica.
5. **Validar** exige que o projeto esteja cadastrado e disponível e que a capacidade exista. **Simular** nunca consulta a API e marca como `SKIP` os nós dependentes. **Executar** mostra diálogo nativo com destino e método, exigindo autorização por execução.
6. Após executar, confira as etapas e eventuais falhas no histórico da pasta do projeto ativo. Os dados reais de entrada/saída não são salvos no histórico.

## Segurança e semântica

- Destino permitido: URLs literais `http://127.0.0.1[:porta]/caminho`. Sem DNS, HTTPS, redes externas, credenciais embutidas, query string, fragmentos ou redirecionamentos.
- POST envia o input JSON validado (até 128 kB); GET não envia corpo, mas seu input ainda é validado. A resposta deve ser JSON, código HTTP 2xx e tamanho até 512 kB.
- Contratos usam apenas um **subconjunto implementado** do JSON Schema: `type` (`object`, `array`, `string`, `number`, `integer`, `boolean`, `null`), `properties`, `required`, `items`, `additionalProperties`; máximo 8 níveis, 30 propriedades por objeto e 8 KiB por contrato. Chaves desconhecidas como `$ref`, `pattern`, `oneOf` ou expressões são **rejeitadas** em vez de ignoradas.
- O contrato é uma configuração local do OmniForge guardada no catálogo em `app.userData`; ele não modifica o código do projeto provedor nem cria uma prova criptográfica de que o serviço na porta pertence àquela pasta. O operador deve verificar a aplicação/porta antes de autorizar.
- Capacidade ausente, projeto offline, timeout, erro HTTP, redirecionamento, resposta inválida ou divergência do schema interrompem a execução dos nós seguintes. Não são fabricadas respostas.
- O registro de capacidade pode ser removido do catálogo sem excluir código dos projetos; fluxos que ainda fazem referência a ela passam a falhar na validação.

## Testes

- `npm test`: cobre persistência, falta de consentimento, POST e GET reais, validação de entrada/saída, URL externa, schema desconhecido, projeto offline, cancelamento, erro, redirecionamento e integridade da pasta provedor.
- `npm run smoke:electron`: no runner Windows, inicia serviço HTTP real, registra o projeto e a API pela interface, confirma/rejeita execução por janela nativa, testa retorno real, simula sem enviar rede e verifica persistência após reiniciar.
- CI é um gate técnico, mas ainda não substitui testes de instalação/desinstalação e segurança operacional numa estação Windows do usuário.
